Most bug bounty hunters, penetration testers and red-teamers use their proxy like a microscope — it shows you what’s happening, but you decide what to look at and what it means. The proxy captures traffic. You review it. You spot a pattern. You test a hypothesis. You create a finding or review findings from passive workflows. I wanted the proxy to think . Not in a vague “AI-powered” marketing sense, but concretely: a proxy that watches traffic in real-time and generates passive detection rules tailored to the target’s specific technology stack. A proxy where right-clicking a request sends it into a persistent AI agent with full hunting methodology. A proxy that refines its own detection rules based on which findings turn out to be true positives and which are noise. A proxy that bridges the gap between “I see interesting traffic” and “an AI specialist is already investigating it.” A year ago, a rare autoimmune disorder left me with significant memory impairment. My reasoning is intact but my ability to retain context across sessions — to remember what I tested last week, to connect a technique I read about to a vulnerability I’m looking at now — is largely gone. Everything you see in this post exists because I needed to build a system that compensates for that. Our shared battle to manage our LLMs persistent memory and context window runs 100% in parallel to my personal battle. By building what my brain needs from AI, I have also been solving some of the more widespread challenges of harnessing the power of AI within it’s current boundaries and limitations. # First - why Obsidian? Throughout this post you’ll see that findings, triaged reports, sitemaps, and hunt state all flow into an Obsidian vault. This isn’t a documentation preference — it’s compensatory infrastructure. I was previously using SQL databases but Obsidian is human readable - which it is essential for me. Bug bounty hunting runs on connections. You read a disclosed report about a CORS bypass on one platform and six months later recognise the same misconfiguration on an unrelated target. You chain a low-severity open redirect with an OAuth state fixation because you’ve seen both patterns before and know they fit together. Those connections used to live and were readily accessible in my head. Now they live in the knowledge graph. Every finding, every piece of research, every hunt session, every technique — they exist as linked markdown files. When I’m investigating CORS on a new target, the graph surfaces my prior CORS research, relevant disclosed reports, the specific bypass techniques I’ve documented, and my own previous findings on similar targets. The links make the connections I can no longer make myself. The system described below writes to this vault continuously — the event bridge appends triaged findings in real-time, the sitemap exporter maps attack surfaces, hunt ledgers track what’s been tested and what hasn’t. The vault has become my external memory, and at this point it’s more comprehensive than my biological memory ever was. This post documents how I built my mastermind-ai system to fully envelop Caido , the Rust-based web proxy that’s completely replaced BurpSuite in my workflow. The architecture involves a custom Caido plugin, a real-time event bridge, 59 GraphQL MCP operations, five systemd daemons, a shared Python infrastructure layer, and a feedback loop that makes the whole system get smarter over time. # Why Caido I switched from BurpSuite to Caido relatively early on in Caido’s journey. The reasons were at first practical: Caido is fast as it is written in Rust, doesn’t require a Java runtime, starts instantly, can be used in browser, CLI and desktop and uses a fraction of the memory. But the real and growing advantage — the one that made this entire integration possible — is architectural. The Three Architectural Advantages GraphQL API — Every operation you can perform in the UI has a corresponding GraphQL query or mutation. Findings, requests, responses, replay sessions, workflows, scopes, hosted files, automate sessions, intercept configuration — all accessible programmatically. The GUI is a GraphQL client. The API is the source of truth. There’s no impedance mismatch between “what the API can do” and “what the tool actually does.” Plugin System — Plugins run as two independent modules: a backend in QuickJS (a lightweight JavaScript engine — not Node.js) and a frontend that renders in the Caido UI. The backend can intercept requests, write to SQLite, make HTTP calls to external services, and send real-time events to the frontend. The frontend can register context menus, add custom pages, show toast notifications, and add items to the sidebar and command palette. Passive Workflows — Node-graph automations that fire on every intercepted request or response. Each workflow is a directed graph of typed nodes: HTTPQL matchers, scope filters, If/Else branching, JavaScript execution, shell commands, finding creation (with dedup via Check Finding ), and row coloring. They’re more powerful than simple pattern-matching — you can run arbitrary logic per-request. But because they’re also manageable via GraphQL ( createWorkflow , updateWorkflow , deleteWorkflow ), they become the substrate for something more interesting: a system that generates and refines its Without the ability to create, modify, and delete workflows programmatically, the whole “proxy that learns” concept would be impossible. # Edit-and-Replay: Preserving Auth Context One of the most practical MCP operations is edit_and_replay . Bug bounty testing is full of repetitive request modification — change a user ID for IDOR testing, swap a header for access control bypass, alter the HTTP method. The naive approach means the agent has to fetch the request, manually reconstruct the raw HTTP with modifications, and handle all the auth headers and cookies itself. edit_and_replay handles this in a single call. It takes a request ID and a set of surgical edits — path, method, headers to set or remove, body, and find/replace patterns — then fetches the original request, applies the modifications to the raw HTTP string while preserving everything else (cookies, auth headers, CSRF tokens), and replays the modified version: // IDOR test — change path, keep all auth edit_and_replay({ request_id : "123" , path : "/api/user/999" }) // Header injection — add X-Forwarded-For, strip CSRF edit_and_replay({ request_id : "123" , set_headers : { "X-Forwarded-For" : "127.0.0.1" }, remove_headers : [ "X-CSRF-Token" ], compact: true // limit response output to ~2000 chars }) The compact , headers_only , and max_body output control flags are available on all request-returning operations ( view_request_by_id , view_response_by_id , sendRequest , edit_and_replay ). They let agents control how much response data enters the context window — compact limits to ~2000 chars and omits the request raw, headers_only strips the body entirely, and max_body sets a custom truncation threshold. This matters when agents are processing dozens of requests in a single investigation. # The Mastermind Plugin This is the centerpiece — a custom Caido plugin that bridges the proxy UI and the Mastermind AI ecosystem. Each entry contains a request ID, host, method, path, and optional hunter specialization. The daemon: Deduplicates — hashes host + path + method + type + hunter to avoid re-investigating the same endpoint Batches — groups requests from the same host (up to 5 per batch) to give the agent connected context Triage gate — manual sends from the Caido plugin bypass triage entirely (you explicitly asked for it, so it gets investigated). Auto-escalations from the event bridge go through Claude Haiku for a quick INVESTIGATE/SKIP verdict Dispatches — sends the batch to the persistent mastermind-ai tmux session via tmux send-keys def send_to_tmux (message: str): """Send investigation request to the persistent mastermind-ai tmux session.""" # Clean message for Claude Code input: # - No backslashes (\ + Enter triggers multi-line mode) # - No pipes or special chars that could confuse input clean = message . replace( " \\ " , "/" ) . replace( "'" , "" ) # Use -l (literal) flag to prevent tmux from interpreting special keys subprocess . run( [ "tmux" , "send-keys" , "-t" , TMUX_SESSION, "-l" , clean], capture_output = True , timeout = 10 , ) # Small delay then send Enter to submit time . sleep( 0.1 ) subprocess . run( [ "tmux" , "send-keys" , "-t" , TMUX_SESSION, "Enter" ], capture_output = True , timeout = 10 , ) The -l (literal) flag is critical — without it, tmux interprets key names in the text (e.g., Enter , Escape ), which corrupts the message. Sending the text and Enter as separate commands with a small delay avoids race conditions with Claude Code’s input handling. The tmux session runs a long-lived Claude Code instance with the full Mastermind context — all 60+ skills, 310+ tools, vault access, and accumulated hunt state. This is different from spawning a new Claude instance per request. Self-adapting workflows act as a heuristic layer — routing detections through ephemeral, target-specific retesting before anything reaches the AI agent. The 50+ permanent passive workflows are a broad detection net. They fire on generic patterns — CORS misconfigurations, DOM sinks, SSRF parameters, open redirects, CSP issues, JWT weaknesses. They’re always on, covering every target. But a detection isn’t a finding. “This response contains dangerouslySetInnerHTML ” tells you the technology exists. It doesn’t tell you whether user input reaches that sink. “This response reflects the Origin header” doesn’t mean credentials are attached. The gap between detection and finding is where most noise lives. The workflow adapter bridges that gap with ephemeral [MM] workflows — machine-generated, target-specific rules that retest deeper and filter signal from noise before escalating to Mastermind-AI. # The Heuristic Architecture [detect] Permanent Workflows [evaluate] Workflow Adapter [retest] [MM] Ephemeral Retest [investigate] Mastermind-AI Investigation Layer 1: Detection — the 50+ permanent workflows fire on every response. They create findings for anything matching their patterns. This is intentionally broad. Layer 2: Heuristic filtering — the workflow adapter daemon watches findings in real-time. When a permanent workflow detects something (e.g., “DOM Sink Collector found innerHTML ”), the adapter evaluates: is this worth retesting? It checks the technology stack, the specific endpoint, and whether this pattern has produced true positives before. Layer 3: Targeted retesting — for findings that pass the heuristic filter, the adapter creates an ephemeral [MM] workflow via Caido’s createWorkflow mutation. This workflow is tighter than the original — scoped to the specific host, watching for the specific confirmation signal. An [MM] workflow might watch for dangerouslySetInnerHTML combined with user-controlled query parameters in the same response. Or it might watch for CORS Access-Control-Allow-Credentials: true specifically on the endpoint where origin reflection was detected. Layer 4: Escalation — only findings from [MM] workflows — the confirmed, retested detections — escalate to the Mastermind-AI queue for deep investigation with specialist hunters. They exist for the duration of a hunt and can be deleted when you move to the next target. This is the key difference from the permanent workflows — those are your persistent detection baseline, while [MM] workflows are the target-specific heuristic layer that comes and goes. The adapter tracks what it has created in a state file, checks for duplicates before creating new workflows, and never recreates a workflow that already exists. When findings are confirmed or dismissed, Haiku evaluates whether to tighten the pattern (reduce noise) or expand it (catch variants). # Noise Control The concern with auto-generated workflows is obvious: more rules = more noise. Three mechanisms keep signal high: Complementary, not duplicating — templates only cover patterns the 50+ permanent workflows don’t already handle. The adapter checks existing workflow names before creating anything. Heuristic filter — findings from permanent workflows pass through the adapter’s evaluation before spawning retests. Not every detection gets an [MM] workflow. Ephemeral lifecycle — [MM] workflows are deleted when the hunt ends. They don’t accumulate across targets. # Enigma Integration Enigma is my custom XSS testing engine — a 5-Rotor mutation system that generates context-aware payloads and tests them in a real browser via Puppeteer. It crawls targets, downloads every JS file, beautifies them, and runs pattern matching against a configurable ruleset — looking for DOM sinks, API keys, hardcoded secrets, debug endpoints, and other security-relevant patterns. The integration has two parts: a js_file_saved hook that auto-beautifies downloaded files, and a js_match_found hook that filters and alerts on high-severity matches. The match alerting hook is where noise control matters most. JXScout finds a lot of matches — console.log calls, generic DOM access, common library patterns. Without filtering, you’d drown in INFO-level noise. The hook implements three layers: # Severity filter — only alert on HIGH+ matches SEVERITY = $( echo " $STDIN_DATA " | jq -r '.severity // "info"' ) CATEGORY = $( echo " $STDIN_DATA " | jq -r '.category // "unknown"' ) case " $SEVERITY " in high|critical ) ;; # proceed * ) exit 0 ;; # skip INFO/LOW silently esac # Dedup — track seen hash(file+line+category) HASH = $( echo " ${ FILE_PATH } : ${ LINE } : ${ CATEGORY } " | md5sum | cut -d ' ' -f1 ) if grep -q " $HASH " " $STATE_FILE " 2>/dev/null; then exit 0 fi echo " $HASH " >> " $STATE_FILE " # Rate limit — max 5 notifications per minute per project RECENT = $( find " $STATE_DIR " -name "*.notify" -newer " $ONE_MIN_AGO " | wc -l ) if [ " $RECENT " -ge 5 ] ; then # Buffer for batch send echo " $MATCH_DATA " >> " $BUFFER_FILE " exit 0 fi HIGH+ matches (secrets, RCE sinks, eval/innerHTML with user input) get appended to /home/mastermind/output/{target}/JXScout-alerts.jsonl and pushed to ntfy.sh for mobile notifications. Evolution This architecture works — it finds bugs, it scales my hunting capability, and it compensates for the memory limitations I live with. But it was built pragmatically, against raw GraphQL, because that’s what was available when I started. Caido has since shipped several features that my integration should align to — the SDK-Client, backend OS modules, and a Python SDK in progress. These are my planned changes to take advantage of what’s now available. SDK-Client (JS) → replacing raw GraphQL in the MCP server. The current MCP server makes 59 raw graphqlRequest() calls with hand-written queries and mutations. Caido’s new SDK-Client provides typed methods — client.requests.list() instead of a 15-line GraphQL string. More importantly, the SDK-Client is designed to be stable across Caido releases. The GraphQL schema breaks between versions; the SDK won’t. This is the single biggest architectural improvement on the roadmap. SDK-Py → replacing raw GraphQL in Python services. The five Python daemons (event bridge, review daemon, queue daemon, workflow adapter, Flask server) all use a shared CaidoClient class that wraps raw GraphQL via urllib / requests . Émile is building a Python SDK that will replace this layer entirely — typed auth, stable client methods, no more inline GraphQL strings. Currently early-stage (auth module complete), but the trajectory is clear. Backend modules → direct OS access from the plugin. The plugin backend currently communicates with external systems entirely via fetch() — HTTP calls to the Flask server, the queue daemon endpoint, the Enigma API. Caido’s backend modules now expose fs , child_process , net , and crypto directly in the QuickJS runtime. This means the plugin could write directly to the investigation queue (filesystem), spawn processes, or interact with local services without the HTTP intermediary. Whether this simplifies or complicates the architecture depends on the use case — the HTTP approach has the advantage of being naturally decoupled — but for latency-sensitive paths like the investigation pipeline, direct access is compelling. Workflow automation via SDK. The self-adapting workflow system currently creates and modifies workflows through GraphQL mutations. The SDK-Client would make this more robust and readable, and potentially expose workflow primitives that aren’t easily accessible via raw GraphQL. Am I becoming a better bug bounty hunter?
