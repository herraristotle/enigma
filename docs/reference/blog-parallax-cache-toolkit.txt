· 53 min read Parallax: A Research-Based Cache Exploitation Toolkit A deep technical exploration of Parallax — a differential cache analysis toolkit built from scratch across 13,000+ lines of Python and Bash, implementing CDN-aware fingerprinting, binary search header testing, byte-level path fuzzing, endpoint discovery, automated weaponization, and exploit classification for web cache poisoning and deception. cache-poisoning cache-deception cdn-security security-tooling parallax The gap between what the cache thinks a request is and what the origin thinks it is — that’s the cache-specific attack surface. Web caching is the invisible backbone of the modern internet. Every CDN, every reverse proxy, every framework-level cache makes the same fundamental promise: store responses and serve them faster. But caching introduces a question that turns out to be devastatingly difficult to answer correctly: what makes two requests “the same”? The answer is the cache key. And every vulnerability in this toolkit exploits the gap between what the cache thinks the key is and what the origin server actually processes. Over the past several months, I built a differential cache analysis toolkit from scratch — 13,000+ lines of Python and Bash across twelve tools — that systematically finds these gaps. Not by guessing. Not by running default wordlists and hoping for the best. By fingerprinting infrastructure, reverse-engineering cache keys empirically, discovering cached endpoints, fuzzing every byte value in the URL path, mining real-world traffic data for headers nobody else tests, auto-classifying the exploits it finds, and weaponizing confirmed findings into verified proof-of-concept chains. This post is about what I built, how it works, and the research and design decisions behind every component. #

What I Wanted to Build I wanted a cache exploitation toolkit that did everything I found myself doing manually — but faster, smarter, and without the gaps. Specifically: CDN-aware intelligent scanning — know what CDN is in play, skip headers that are already keyed, and use CDN-specific oracles when available Multi-signal response diffing — detect influence beyond simple string reflection: status changes, body size deltas, new response headers, security header modifications Integrated WCP + WCD — cache poisoning (injecting content) and cache deception (stealing content) tested in a single pipeline, because they share infrastructure fingerprinting Data-driven wordlists — headers mined from real web traffic via BigQuery, not static lists that go stale Automated exploit classification — when I find an unkeyed input, tell me what the impact is: XSS, redirect, CP-DoS, session fixation, CSP bypass Scalable architecture — binary search to test 10,000+ headers in ~560 requests, not 10,000 sequential ones I set out to build something purpose-built for the problem. # 
Research Foundations This toolkit stands on the shoulders of several years of cache exploitation research, both academic and practitioner-driven. Understanding the lineage matters, because every design decision traces back to a specific insight from this body of work. # 
James Kettle and the Birth of Cache Poisoning (2018-2020) James Kettle’s “Practical Web Cache Poisoning” (2018) defined the attack class. His core insight: HTTP headers that influence the response but aren’t included in the cache key are effectively invisible inputs. An attacker who finds one can inject content that gets served to every subsequent visitor. His follow-up, “Web Cache Entanglement” (2020), extended this to unkeyed query parameters, fat GET requests (where body parameters override query parameters but the body is never part of the cache key), and parameter cloaking (exploiting parser differentials between the cache and the origin). I took his foundational idea — automated unkeyed input discovery — and rebuilt it with CDN awareness, multi-signal diffing, binary search for scalability, and a 10,000-header wordlist. # 
Martin Doyhenard and Path Confusion (DEF CON 2024) Martin’s “Gotta Cache ‘Em All” talk at DEF CON 32 is the definitive work on cache deception via path confusion. His key contribution: the mismatch between how CDNs and origin servers interpret specific bytes in URL paths is not random — it’s systematic and predictable per vendor/framework combination. A semicolon ( ; ) is a matrix variable delimiter in Spring. A null byte ( %00 ) truncates paths in OpenLiteSpeed. A dot ( . ) is a format suffix in Rails. If the CDN doesn’t recognize these as delimiters but the origin does, you get cache deception: the origin serves /profile while the CDN caches it as /profile;anything.css . My cache_diff tool automates exactly this: byte-level differential fuzzing across 256 byte values, three path positions, and three encoding levels, per endpoint. That’s up to 2,304 probes per URL, where manual testing typically covers five to ten known delimiters. # 
Iustin Ladunca (Youstin) and the Data Advantage (~$40K, 70+ bugs) Youstin industrialised cache poisoning discovery. His 2024 write-up describes how he used Google BigQuery against the HTTP Archive dataset to build a header wordlist from real web traffic — headers that actually appear in the wild but aren’t in any static wordlist. He extracted Vary header values to identify which headers CDNs actually key on, then tested the rest as potential unkeyed inputs. Eighty percent of his findings were CP-DoS via unkeyed headers. He found bugs in Apache Traffic Server, Cloudflare, GitHub ($7,500), GitLab ($4,850), and Fastly. I took his BigQuery approach and scaled it. My header_harvest tool queries HTTP Archive for uncommon response headers (the “long tail” appearing on 10-5,000 sites) and Vary-listed headers. Combined with IANA’s HTTP Field Name Registry and CDN-internal header documentation, I assembled a 10,244-header wordlist. # 
HCache and “The Internet’s Invisible Enemy” (CCS 2024) Hoang et al.’s “HCache: The Internet’s Invisible Enemy” (ACM CCS 2024) is the most systematic empirical study of Cache Poisoned Denial of Service to date. They tested the Tranco Top 1K against 14 distinct CP-DoS attack types and found 225 vulnerable websites — far more than previous estimates suggested. Their key insight: most CP-DoS scanners only test “obvious” payloads — oversized headers, conflicting Transfer-Encoding values, bogus Content-Length on GET requests. These are the attacks that Nguyen-Phuc et al. originally described in 2019. But HCache showed that five additional attack classes account for a significant portion of real-world CP-DoS: RFC-compliant malformed conditionals (HCache attacks 3, 5, 6): Headers like If-Match , If-Range , and If-Modified-Since with syntactically valid but semantically wrong values. If-Match: 123456789 isn’t a valid ETag format — origins respond with 412 Precondition Failed. If-Modified-Since: Thu, 01 Jan 2099 00:00:00 GMT is a valid HTTP date in the future — origins respond with 304 Not Modified (no content body). If these error responses get cached, every subsequent user gets denied the actual page content. The headers themselves are perfectly legitimate RFC 7232/7233 headers with valid syntax — they just provoke error responses. WAFs don’t flag them because there’s nothing malicious about a conditional request. Malformed range requests : Range: bytes=cow (non-numeric), Range: bytes=9-4 (reversed), Range: bytes=-0 (zero suffix-length), Range: invalid (missing bytes= prefix). Each triggers a 416 Range Not Satisfiable or 400 Bad Request from standards-compliant origins. These are particularly dangerous because many CDNs pass Range headers through to the origin without validation. Protocol upgrade poisoning : Upgrade: HTTP/0.9 , Upgrade: WebSocket (without the required handshake headers), Upgrade: h2c (cleartext HTTP/2 when the connection isn’t TLS-appropriate). Origins that respect RFC 7230 respond with 426 Upgrade Required. Cached 426 responses deny service and confuse clients. WAF-triggered denial : This is the most counterintuitive class. A WAF designed to protect the site becomes the denial vector. Sending User-Agent: sqlmap/1.0 or X-Custom-Header: ' OR 1=1 -- triggers a 403 from the WAF layer. If the CDN caches the WAF’s block page (which many do — the block page is a “valid” 403 response from the CDN’s perspective), every subsequent user gets the block page instead of the real content. The attacker never even reaches the origin. HCache found this pattern on sites protected by Cloudflare, Akamai, and Imperva. Metacharacter injection (HCache attack 10): Control characters embedded in header values — SOH ( \x01 ), BS ( \x08 ), ESC ( \x1b ), DEL ( \x7f ) — cause protocol-level errors or trigger WAF anomaly detection that produces cacheable error responses. Not all control characters work: h11 (Python’s HTTP/1.1 parser, used by httpx and uvicorn) rejects \x00 , \x0A , \x0B , \x0C , \x0D at the transport layer. But the remaining control bytes pass through h11 and can trigger errors on the origin. Before reading this paper, my scanner had 9 CP-DoS payloads — all in the “oversized/conflicting” category. After implementing HCache’s attack taxonomy and continuing to expand the payload set, it now has 56 payloads across four classified attack types: traditional CP-DoS (oversized headers, conflicting encodings), RFC-compliant malformed values (conditionals, ranges, upgrades, metacharacters), WAF poisoning (16 tool signatures and attack patterns), and illegal header name injection (5 raw-socket payloads for Akamai). The scanner covers all 14 of HCache’s attack types. The 304-as-denial case deserves special attention. A cached 304 Not Modified is arguably worse than a cached 400 or 500 — because the 304 has no body. Users get a completely empty response. And because If-Modified-Since is a standard conditional header that CDNs routinely pass through, many caching configurations don’t strip it. The attack requires only a single request with a future date. # 
The RAID 2024 Paper and Hidden Caches Golinelli and Crispo’s “Web Cache Deception Escalates!” (RAID 2024) revealed that 5.8% of Tranco Top 50K websites have caches that don’t advertise themselves via standard headers. No X-Cache , no CF-Cache-Status , no Age header. They’re invisible. Their detection method: send paired HTTP/2 requests simultaneously — one with a fresh cachebuster, one reusing a fixed cachebuster — and compare timing. If the fixed request is consistently faster, there’s a cache. They used Welch’s t-test for statistical significance. My cache_timing tool implements their algorithm. It also contributed a practical finding I incorporated into the HTTP client: query-string cache busting only works on 60.4% of sites. Adding Origin , X-Forwarded-Host , and X-Forwarded-Scheme headers as supplementary cache busters increases coverage to 84.3%. # 
The ChatGPT Account Takeover and the Cloudflare Bypass Two case studies directly shaped the toolkit’s design. The ChatGPT ATO ($6,500): Cloudflare didn’t decode %2F..%2F in paths, but OpenAI’s backend did. A URL like /share/%2F..%2Fapi/auth/session stayed encoded for Cloudflare’s cache key (it matched the /share/* caching rule) but the backend resolved it to /api/auth/session and returned authentication tokens. Victim visits the link, their tokens get cached, attacker reads the cache. This is exactly the kind of encoding-level normalization mismatch that cache_diff tests systematically at single, double, and triple encoding depths. The Cloudflare duplicate header bypass: Cloudflare deployed a WAF rule adding X-Forwarded-Host to the cache key to prevent poisoning. But the cache key evaluation only checked the first instance of duplicate headers. Sending two X-Forwarded-Host headers — one clean (matching the real host), one malicious — meant the cache keyed on the clean value while the backend processed both. My cache_poison tool tests this explicitly via its duplicate header bypass module. #

Stage 1: Data Collection — header_harvest (308 lines) This is where the data advantage comes from. Instead of shipping a static wordlist, I query Google BigQuery against the HTTP Archive — the world’s largest public dataset of real HTTP responses, crawled monthly across millions of domains. Two queries power the wordlist: Uncommon headers query : Find response headers appearing on 10 to 5,000 sites. Below 10 is noise. Above 5,000, everyone already tests for it. The sweet spot is the long tail — headers that real servers send but no wordlist includes. My January 2026 harvest yielded 8,595 uncommon headers. -- Pseudocode: query HTTP Archive for response headers
 -- appearing on 10-5,000 distinct sites (the long tail)
 SELECT header_name, COUNT ( DISTINCT site) AS sites 
 FROM httparchive_responses 
 GROUP BY header_name 
 HAVING sites BETWEEN [low_threshold] AND [high_threshold] 
 ORDER BY sites ASC 
 Vary analysis query (inspired by Youstin’s technique): Extract headers listed in Vary response headers, excluding the obvious ones ( Accept-Encoding , User-Agent , etc.). Headers in Vary are explicitly used for cache keying. If an attacker can control them, they might poison the cache for a specific Vary partition. This yielded 1,875 headers. -- Pseudocode: extract Vary-listed headers, excluding
 -- the obvious ones (Accept-Encoding, User-Agent, etc.)
 -- Split comma-separated Vary values, count by site frequency
 SELECT header_name, occurrences, sites 
 FROM parsed_vary_headers 
 WHERE header_name NOT IN ([standard_headers]) 
 ORDER BY sites DESC 
 The wordlist_builder (427 lines) then merges these BigQuery results with 145 CDN-internal headers (documented but rarely tested) and 39 IANA-registered headers. Deduplication, filtering, and frequency-based prioritisation produce two output wordlists: headers-fast.txt (379 entries): High-probability headers for quick scans headers-all.txt (10,244 entries): The full corpus for exhaustive scans #

Stage 3: Detection — cache_timing (465 lines) Some caches are invisible. No X-Cache header, no Age , no CF-Cache-Status . Golinelli and Crispo found 5.8% of major websites have these hidden caches. cache_timing implements their paired-request timing algorithm over HTTP/2 multiplexing. It sends batches of paired requests — one “randomised” pair (both cache-busted, establishing a noise baseline) and one “fixed” pair (one busted, one reusing a cachebuster, potentially served from cache). After collecting enough samples, a Welch’s t-test determines whether the timing difference is statistically significant. This is the kind of capability that separates a scanner from a toy. If you can’t detect a cache, you can’t test it. # 
Stage 4: Cache Poisoning — cache_poison (3,649 lines) This is the largest and most complex tool in the toolkit — and the one that’s grown the most since the initial release. It finds unkeyed inputs that influence cached responses, verifies that the poisoned response actually gets served from cache, and classifies the exploit type. Across 24 distinct test methods, it covers headers, cookies, query parameters, URL path manipulation, body parameters, HTTP/2 pseudo-headers, framework-specific caches, OAuth endpoints, cache invalidation methods, and cross-input WAF bypass techniques. Multi-Signal Response Diffing Rather than checking a single signal — whether a canary string appears in the response body — I check five: Body reflection — canary in response body, classified by HTML context (script tag, attribute URL, link tag, meta tag, image tag, form tag, inline style, generic HTML). Header reflection — canary in Location , Set-Cookie , Link , Content-Location , X-Redirect-URL , Refresh , or Content-Type response headers. Status code change — the header causes a different HTTP status (301, 302, 400, 500, etc.). Body size delta — the response grows or shrinks by more than 5% (content added or removed). New response headers — headers appear in the test response that weren’t in the baseline (debug mode activated, different backend path). Additionally, I monitor changes to security-relevant headers: Content-Security-Policy , X-Frame-Options , Strict-Transport-Security , Cross-Origin-Resource-Policy , and others. If an unkeyed header weakens a cached security header, that’s a critical finding even without any body reflection.  Binary Search for Scalability Testing 10,244 headers sequentially would require 10,244 requests — slow and loud. Instead, I batch headers into groups of 20, send all 20 in a single request with a shared canary, and diff against the baseline. If the group shows no signal, I skip all 20 headers in one request. If it shows a signal, I binary search within the group (log2(20) ~ 5 requests) to isolate which header(s) caused it. Each group gets its own cachebuster to prevent cross-group cache pollution. If a group test returns 431 (Request Header Fields Too Large) — because 20 extra headers exceeded the server’s limit — the scanner automatically splits into smaller sub-groups and retries. A subtlety: binary search can miss AND-gated behaviours where header A only influences the response when header B is also present. When neither half alone differs but the full group did, I run pairwise interaction testing on the top candidates from each half. This catches the “multiple headers needed together” scenarios. Performance : 10,244 headers → ~512 groups + ~50 binary searches ~ ~560 requests. The fast wordlist (379 headers) takes about 25 requests for the group phase. A limitation: the binary search runs to full isolation even when it’s clear a group has only one influencing header. Early stopping after the first negative half-split — when one half shows zero signal — would halve the remaining search depth. This is a planned optimisation that would reduce the ~50 binary searches to ~35 on average. Cache Key Oracle For every header that influences the response, I need to determine whether it’s in the cache key. This is the difference between “interesting” and “exploitable.” The test: # Step 1: Prime cache WITH the header + unique cachebuster + pinned UA 
 oracle_cb = f "cb=oracle_ { random . randint( 100000 , 999999 ) } " 
 oracle_url = f " { url } ? { oracle_cb } " 
 pinned_ua = "Mozilla/5.0 (Windows NT 10.0; Win64; x64) ..." 
 await client . get(oracle_url, headers = {header: canary, "User-Agent" : pinned_ua})
 # Step 2: Request WITHOUT the header, SAME cachebuster + SAME UA 
 await asyncio . sleep( 0.3 ) # allow cache propagation 
 verify = await client . get(oracle_url, headers = { "User-Agent" : pinned_ua})
 # Step 3: Check if canary persists without the header 
 verify_body = verify . body_preview . decode( "utf-8" , errors = "ignore" )
 if canary in verify_body:
 # Header is NOT in cache key → CONFIRMED cache poisoning 
 confidence = "CONFIRMED" 
 If the canary persists without the header being sent, the header is NOT in the cache key. This is confirmed cache poisoning. A critical detail: the User-Agent must be pinned to the same value for both the prime and verify requests. Many CDNs include Vary: User-Agent in their responses, which partitions the cache by User-Agent. If the scanner rotates User-Agents between requests (as my HTTP client does for fingerprint diversity), the prime and verify hit different cache partitions and the oracle always reports “not cached” — a false negative. This bit me during early testing and is now fixed across all oracle call sites: main oracle, cookie oracle, interaction oracle, and parameter cloaking oracle. Exploit Auto-Classification When a reflected unkeyed header is confirmed, I classify where the canary landed: In a <script> tag or src / href attribute → XSS (inject JavaScript via the poisoned CDN response) In a Location: header → Open redirect (all users redirected to attacker’s domain) In a Set-Cookie: header → Session fixation (inject cookies via cache) In a <meta> tag → CSP bypass potential Causes a 4xx/5xx that gets cached → CP-DoS (cache serves errors to everyone) Security headers weakened → Security header poisoning (CSP removed, XFO removed) Response content changes without reflection → Behaviour poisoning Beyond Basic Headers The scanner also tests: Unkeyed cookies : Extract cookie names from Set-Cookie response headers, then test each as an unkeyed cache input. For every cookie, inject a canary value with a cachebuster, then run the standard cache key oracle. This catches an entire class of cache poisoning that header-only scanners miss — server-set cookies that influence the response but aren’t part of the cache key. Unkeyed query string detection : A two-phase test that runs before any header testing. Phase A sends two requests with different query strings — if the second returns a cache HIT with an identical body hash, the entire query string is unkeyed. Phase B confirms by poisoning a canary into the cache via query parameter, then checking if the bare URL serves it. When the query string is unkeyed, the scanner warns that query-parameter-based cache busters are ineffective and switches to header-based busting. Parameter cloaking : Exploits parser differentials where the cache treats a semicolon ( ; ) as part of a parameter value, but the backend treats it as a parameter delimiter. For each unkeyed parameter found, the scanner tests unkeyed=x;target=canary against all existing URL parameters plus high-value targets (JSONP callbacks, redirect parameters, template names). A successful cloak means an attacker can override keyed parameters through an unkeyed one — the cache sees one parameter, the origin sees two. # Parameter cloaking: semicolon delimiter differential 
 # Cache sees: utm_content=x;callback=alert(1) ← single param value 
 # Origin sees: utm_content=x AND callback=alert(1) ← two separate params 
 cloak_value = f "x; { target } = { canary } " 
 cloak_url = f " { url } & { unkeyed } = { cloak_value } & { cachebuster } " 
 URL path normalization detection : A 2-request test that detects when a cache decodes percent-encoded bytes before computing the cache key, but the origin does not. First, send a request to a nonexistent path and check if the path is reflected in the 404 body. Then send the same path with one character percent-encoded (e.g., c → %63 ) and check if the cache returns a HIT. If it does, the cache normalizes encoding before keying — meaning /<script> and /%3cscript%3e share a cache key. This enables XSS via cache poisoning: the attacker sends the literal <script> tag (which gets cached), victims visit the innocuous-looking encoded URL, and the cache serves the poisoned XSS response. # Path normalization: cache decodes %XX before keying

 AND-gate header interactions : When a header causes a same-host redirect (e.g., x-forwarded-scheme: http → 301 redirect to HTTPS), the scanner automatically tests it in combination with host-override headers. The goal: find multi-header combinations where one header triggers the redirect mechanism and a second header controls the destination. This catches scenarios like Cloudflare’s x-forwarded-scheme + x-forwarded-host combo, where neither header alone produces an exploitable response but together they create an open redirect via cache poisoning. Only ~8 extra requests per redirect finding. Content negotiation poisoning : Accept: application/json instead of text/html — if the JSON response gets cached as the HTML page, it’s a content-type confusion attack. Method override caching : X-HTTP-Method-Override: POST on a GET request — some frameworks process it as POST but the cache stores it as GET. Fat GET : Body parameters on GET requests that override query parameters, where the body is never part of the cache key. HTTP/2 Host confusion : :authority pseudo-header vs Host header mismatches where the CDN keys on one but the origin routes on the other. Unkeyed query parameters : CloudFront and some Akamai configurations forward query parameters to the origin without including them in the cache key. Normalization bypasses : For headers that ARE keyed, test case variants ( x-forwarded-host vs X-FORWARDED-HOST ), whitespace-prefixed values, and duplicate headers with case variants — exploiting the gap between how the CDN normalises the key and how the backend processes the value. Duplicate header bypass : Send two instances of a header, first clean (keyed), second malicious (processed by backend). New Attack Modules (Since Initial Release) The following modules were added to address attack surfaces I identified after operational testing: Fragment forwarding (CVE-2021-27577): Tests whether %23 (percent-encoded # ) is forwarded to the origin but stripped from the cache key. Apache Traffic Server had this vulnerability — it decoded %23 to # server-side, forwarded the fragment to the origin, but excluded everything after # from the cache key. If a canary injected after %23 reflects in the response body, it’s an unkeyed input. Combined with XSS payloads, an attacker can poison the cache via GET /page%23<script>alert(1)</script> and victims visiting /page receive the poisoned response. Cache invalidation method testing : Tests whether unauthenticated PURGE , BAN , REFRESH , INVALIDATE , or FASTLYPURGE HTTP methods are accepted. If any method returns 200 or 204 without authentication, an attacker can flush the cache at will — turning any single-use cache poisoning finding into persistent exploitation by re-poisoning after each flush. Next.js ISR/SSG framework cache : Gated by the fingerprinting module (only runs when primary_framework == "nextjs" ). Tests CVE-2024-46982 (zhero’s disclosure): the X-Middleware-Prefetch: 1 header causes Next.js ISR to cache the JSON/RSC payload instead of HTML. Also tests RSC: 1 for React Server Component request manipulation and Next-Router-State-Tree for layout poisoning. These are framework-level cache poisoning vectors that operate independently of the CDN cache layer. Import hijacking escalation : When the scanner finds a confirmed cached redirect (via an unkeyed header like X-Forwarded-Host ), it automatically escalates by testing JS and CSS import URLs. It parses <script src> and <link rel=stylesheet href> tags from the baseline response, then tests each import URL with the same redirect-causing header. If an import URL is also redirectable via the same unkeyed header, the attacker controls where the browser loads scripts from — stored XSS on every page that includes the import. This is Kettle’s 2018 import hijacking technique, automated. Illegal header name injection : An Akamai-specific module that bypasses httpx entirely, using raw TCP sockets to send headers with illegal characters in the name (not just the value). Characters like SOH ( \x01 ), space, colon, tab, and DEL in header names cause the origin to return 400 Bad Request, and Akamai caches the error. This required dropping to socket.create_connection() + ssl.wrap_socket() because httpx (and h11) validates header names at the transport layer — the very restriction that makes this attack interesting, since it means most automated scanners can’t even attempt it. # Raw socket bypass for illegal header name characters

 Payload splitting (cross-input WAF bypass): When the scanner finds both a reflected unkeyed header AND a reflected unkeyed cookie, it tests splitting a canary across them — header gets the first half, cookie gets the second half. If both halves appear adjacent in the response, the WAF inspects each input individually (seeing neither as malicious), but the combined reflection in the cached response reconstructs the full payload. Surrogate-Key/Control injection : Gated by CDN detection (only runs on Fastly, Cloudflare, or Varnish). Tests whether Surrogate-Key , Surrogate-Control , or CDN-Cache-Control headers are processed from the client request. Surrogate-Key injection controls purge groups — an attacker can tag cached responses and selectively invalidate them. Surrogate-Control: max-age=31536000 extends TTL from minutes to a year, making any cache poisoning finding persist far longer than the natural TTL. CDN-Cache-Control: max-age=31536000, public is the Cloudflare variant. OAuth/OIDC endpoint poisoning : Probes 10 standard OAuth endpoints ( .well-known/openid-configuration , .well-known/oauth-authorization-server , /oauth/authorize , /oauth/token , /oauth/callback , etc.) and tests whether host-override headers ( X-Forwarded-Host , X-Forwarded-Prefix , X-Original-URL ) influence their responses. This implements the Herish Part 3 / PayPal $30,750 technique: poisoning .well-known/openid-configuration to redirect authorization_endpoint and token_endpoint to an attacker server, hijacking all OAuth flows that rely on the discovery document. Multi-CDN layer mismatch testing : When the fingerprinting module detects multiple CDN or proxy layers (e.g., Cloudflare in front of Varnish), tests whether headers that pass through the outer CDN layer can poison the inner cache. A header keyed by the outer CDN (accepted, forwarded) but unkeyed by the inner cache (influences response, not part of key) produces an exploitable mismatch. Tests 6 commonly-different headers ( X-Forwarded-Host , X-Forwarded-Proto , X-Forwarded-Port , X-Forwarded-Prefix , X-Original-URL , X-Rewrite-URL ).  Multi-Profile and Vary-Based Scope For confirmed poisoning findings, I determine the blast radius. If the target’s Vary header includes the poisoned header, the poisoning is “targeted” — only users sending that specific header value get the poisoned response. Otherwise, it’s “global” — every user gets poisoned. I also test cache partitioning by device type (desktop, mobile, Googlebot User-Agent) to determine whether a desktop-targeted poison affects mobile users or vice versa. Internal and Application-Level Cache Support Not all caches announce themselves. CDN-fronted caches have X-Cache , CF-Cache-Status , or Age headers. But application-level caches — Rails fragment caching, Django template fragment caching, custom in-memory stores — have no external indicators. No cache headers, no Age , no status fields. The RAID 2024 paper found 5.8% of major websites have these hidden caches. The scanner handles this at three levels: First, target URL preference . When the scanner finds an external cache on a static file (like /favicon.ico ) but the user specified the homepage, it tests headers against both URLs. Many internal caches only affect dynamic pages — testing against a static asset would miss every finding. The scanner always prioritizes the user-provided URL for header influence testing: if found_url != target:
 # External cache confirmed on static file, but test headers against target 
 result . cached_url = target
 Second, fallback when no external cache is detected . If find_cacheable_url can’t confirm any external cache via headers, it still returns the target URL instead of giving up. This ensures internal/application-level caches get tested even when they’re invisible. Third, multi-request oracle priming . When the standard single-request oracle fails (header is reflected but canary doesn’t persist from one request to the next) and no CDN is detected, the scanner enters an internal cache priming mode: it sends 20 consecutive requests with the poisoned header, waits for propagation, then verifies. Application-level caches often require multiple writes before a fragment cache entry gets overwritten: if not canary_persisted and diff . is_reflected and not self . cdn_name:
 # Internal cache? Try sustained priming 
 for _ in range( 20 ):
 await self . client . get(oracle_url, headers = prime_headers)
 await asyncio . sleep( 0.5 )
 verify = await self . client . get(oracle_url) # no poison header 
 canary_persisted = canary in verify . body
 This 20-request priming adds ~10 requests per reflected header without a CDN, but it catches an entire class of vulnerabilities that external-cache-only scanners miss entirely. # 
Set-Cookie Cacheability Gate A subtle cache behaviour affects many real-world targets: CDNs and reverse proxies often refuse to cache responses that contain Set-Cookie headers. This means first-visit responses (which set session cookies) are never cached, while subsequent requests from cookied users are cacheable. The scanner handles this naturally through httpx’s built-in cookie persistence. Within a scan session, httpx’s AsyncClient automatically stores cookies from Set-Cookie responses and replays them on subsequent requests — exactly mirroring how a real browser behaves. The first request to a target gets the Set-Cookie + no-cache response. The second request carries the session cookie, the server omits Set-Cookie , the CDN sees a cacheable response, and the scanner detects the cache correctly. This is not a feature I had to build — it’s a consequence of using httpx correctly. But it’s worth noting because it explains why manual testing with curl (which doesn’t persist cookies between invocations) produces different results than the scanner: curl always looks like a first-time visitor, so the page always appears uncacheable. CP-DoS: Three Attack Classes Cache Poisoned Denial of Service is the simplest form of cache poisoning — instead of injecting useful content, you inject an error. If the error response gets cached, every subsequent user gets served the error instead of the real page. My initial implementation had 9 payloads, all in the “oversized/conflicting” category that Nguyen-Phuc et al. described in 2019 and Youstin found extensively in the wild. After studying HCache’s systematic taxonomy (CCS 2024) and continuing to expand the attack surface, I now have 56 payloads across four classified attack types, each with its own detection method: Class 1: Traditional CP-DoS ( attack_class: "cpdos" ) — 35 payloads The original approach: send headers that cause the origin to return error status codes. They’re loud — WAFs catch the oversized ones easily — but they still work on a surprising number of targets because many CDNs process and cache the error before the WAF layer evaluates the request content.  The 304 case is important. Previous CP-DoS scanners only watch for 4xx and 5xx status codes. But a cached 304 is arguably worse — the response has no body at all. Every user who hits the cached entry gets an empty page with a 304 status, which most browsers interpret as “nothing has changed” and show stale or blank content. And because If-Modified-Since is a standard conditional header that CDNs routinely pass through to the origin, many caching configurations don’t strip it. The irony is acute: the site operator deployed a WAF to prevent attacks, and the WAF’s own block responses become the attack vector. Class 3: Metacharacter Injection ( attack_class: "meta_char" ) — classified within Class 1 Metacharacter payloads are technically part of the CPDOS_PAYLOADS list but classified separately in findings output. They use control bytes that pass through Python’s h11 HTTP parser but cause errors at the origin. The specific bytes chosen — \x01 (SOH), \x08 (BS), \x1b (ESC), \x7f (DEL) — are the survivors after h11’s transport-layer rejection of \x00 , \x0A , \x0B , \x0C , \x0D . These are tested in both custom headers ( x-metachar-test ) and standard headers ( accept , accept-encoding , content-type ) because origin servers may validate standard headers differently from unknown ones. Class 4: Illegal Header Name Injection ( attack_class: "illegal_header_name" ) — 5 payloads This class targets a transport-layer blind spot. While metacharacter injection (Class 3) puts control bytes in header values , illegal header name injection puts them in header names — X-Illegal\x01Test , X-Illegal Test (space), X-Illegal:Test (colon), X-Illegal\tTest (tab), X-Illegal\x7fTest (DEL). These are specifically effective against Akamai, which forwards headers with illegal name characters to the origin. The origin returns 400 Bad Request, Akamai caches the error. The implementation is notable because it’s the only module that drops below the httpx abstraction layer. httpx (via h11) validates header names at the transport layer and rejects names with control characters or spaces. The scanner uses raw TCP sockets with optional TLS wrapping to bypass this validation — constructing the HTTP request as a byte string and sending it directly. This makes the attack impossible to test with standard HTTP libraries, which is partly why it’s been underexplored. Request Budget The full CP-DoS + WAF poisoning suite adds 102 requests in the worst case (51 payloads × 2 each for test + verify, plus the 5 illegal header name payloads which use raw sockets). In practice, most payloads won’t trigger error responses on any given target, so the verify phase is skipped — the real cost is closer to 55-65 requests. At 10 requests/second, that’s about 6-7 seconds of additional scan time. Stage 2½: Endpoint Discovery — discover (634 lines) Before the initial release, I scanned a single URL per domain — usually the homepage or a known cached static file. This missed vulnerabilities that only manifest on specific endpoints. discover solves this by finding all cached endpoints before scanning. Discovery pulls URLs from four sources: Static wordlist ( data/cacheable-paths.txt , 40 paths) — common cacheable paths like /robots.txt , /favicon.ico , /sitemap.xml , API endpoints Katana (live crawl) — headless browser-based crawling to find dynamic links the site actually serves Gau (archive data) — pulls historical URLs from Wayback Machine, Common Crawl, OTX AlienVault, and URLScan.io BigQuery HTTP Archive — queries the HTTP Archive dataset for known paths on the target domain The deduplication is structural, not string-based. /product/123 and /product/456 collapse into a single representative endpoint — the scanner tests the pattern , not every instance. This prevents scanning thousands of product pages when one representative covers the attack surface. Each discovered URL goes through a two-request cacheability oracle: prime the path, sleep, then verify whether a cache HIT occurs. Only confirmed-cached endpoints proceed to the diff and poison stages. The result is a DiscoveryResult with a cached_endpoints list that drives all downstream scanning. # 
Stage 6: Weaponization — weaponize (1,004 lines) Raw scan output tells you “this delimiter causes a mismatch.” Weaponize turns that into a proven exploit chain with impact assessment and a ready-to-submit proof of concept. The four-phase pipeline: Phase A: Discover sensitive endpoints. Crawls the target for pages containing authentication indicators (CSRF tokens, session cookies, emails, API keys, __NEXT_DATA__ , __INITIAL_STATE__ ). These are the endpoints where cache deception has real impact — leaking session data, not just static HTML. Phase B: Verify delimiters per endpoint. Takes confirmed delimiters from cache_diff output and verifies each one still works against every sensitive endpoint. A delimiter that works on /profile may not work on /api/me — different backend routes can have different parsing behaviour. Phase C: Assess impact. For each working delimiter + endpoint combination, extracts and classifies what’s in the response: CSRF tokens → token_leak Session cookies in Set-Cookie → ato (account takeover) Email addresses / PII → pii_leak JSON with sensitive keys → content_leak __NEXT_DATA__ / __INITIAL_STATE__ → checks for embedded auth data Phase D: Generate PoC URLs. Produces ready-to-use proof-of-concept URLs with the delimiter and a static extension that triggers caching. Each PoC includes the victim URL, the attacker read URL, exploitation steps, and an exploitability score (auth indicators +3, sensitive data +3, cached +2, JSON +1). Weaponize can ingest cache_diff JSON output directly, so the full chain is: cache_diff finds mismatches → weaponize turns them into scored, verified exploits. # 
Orchestration — batch_scan (664 lines) The batch scanner ties everything together for multi-URL campaigns. The pipeline is now: probe → discover → per-endpoint (diff + poison) → weaponize . Design Decisions and Trade-Offs Why Python, not Go or Rust? Speed is not the bottleneck. Network I/O is. A cache exploitation scanner spends 99% of its time waiting for HTTP responses. Python’s asyncio with httpx provides excellent async HTTP/2 support, and the development velocity advantage let me iterate faster on the detection logic, which is where the real complexity lives. Why binary search instead of concurrent group testing? I tested sending all 10,000 headers simultaneously partitioned across concurrent requests. The problem: many targets have header size limits (431 errors), rate limits that kick in faster with concurrent requests, and WAFs that flag traffic patterns. Binary search is slower in wall-clock time but dramatically more reliable and stealthier. Why canary-based detection instead of pure diffing? Pure response diffing (comparing body hashes) produces false positives from dynamic content: timestamps, CSRF tokens, ad slots, A/B test variants. Canary-based detection — checking whether my specific injected value appears in the response — is more precise. I use pure diffing only as a secondary signal (size delta, new headers, status change) where canary detection doesn’t apply. Why headless CLI instead of a GUI? Independence from desktop tooling matters for automation at scale. My tools run headless on a VPS, produce JSON output, and integrate with any pipeline. # 
What I Learned CDN documentation ’lies’. Not intentionally — but documentation describes defaults, and real-world configurations are customised per-property. I found Cloudflare deployments where X-Forwarded-Host was NOT in the cache key (despite being a default), and Akamai deployments where the debug headers were blocked. Empirical cache key reversal — testing what’s keyed by observing behaviour — is the only reliable approach. Body hash normalisation is critical. Before I added the Cloudflare email obfuscation normalisation, every Cloudflare-fronted target produced false positives in the diff engine. Same page, different data-cfemail values, different hashes. One regex fixed months of frustration. Header size limits are a real constraint. About 30% of targets return 431 (Request Header Fields Too Large) when I send 20 custom headers simultaneously. The adaptive group-size reduction — splitting into sub-groups of 5 on 431 — was essential for reliability. The long tail is where the money is. The headers that yield findings are rarely the well-known ones. They’re custom headers from specific frameworks, CDN-internal headers that were documented once in a blog post, and proxy headers that developers added for debugging and forgot to remove. The BigQuery harvesting pipeline finds these. Internal caches are a different beast. External CDN caches are predictable: send one request with a poison header and a cachebuster, wait, verify. Application-level caches (Rails fragment caching, Django template caching, custom in-memory stores) don’t respond to a single write. They need sustained priming — sometimes 20+ requests — before a cached fragment gets overwritten. This makes automated confirmation unreliable: a single-attempt oracle will always say “not cached” even when the header has real influence. The right approach is to detect the influence (header reflected in response) and flag it as PROBABLE when no CDN is detected, then optionally attempt sustained priming for confirmation. Test the right URL. A scanner that picks /favicon.ico for testing because it’s obviously cached will miss every vulnerability that only affects dynamic pages. Static files don’t have JavaScript sinks, template variables, or reflected parameters. Always test headers against the user’s intended target URL, not just the first cacheable static resource you find. Your HTTP client’s cookie handling matters more than you think. Many CDNs refuse to cache responses with Set-Cookie headers. If your scanner doesn’t persist cookies across requests within a session, it always looks like a first-time visitor, always gets Set-Cookie , and concludes the page is uncacheable. A real browser (or an HTTP client that handles cookies) sends the cookie on the second request, the server omits Set-Cookie , the CDN sees a cacheable response, and the vulnerability becomes testable. This is why manual curl testing can give different results than automated scanning with httpx — curl doesn’t persist cookies between invocations. CP-DoS is not one attack — it’s a taxonomy. Before reading HCache, I treated CP-DoS as a single technique: send a bad header, get an error cached. After implementing their full attack taxonomy, I realised I’d been testing less than a third of the attack surface. The RFC-compliant conditional header attacks are particularly insidious because they use completely legitimate HTTP headers with completely legitimate syntax. If-Modified-Since: Thu, 01 Jan 2099 00:00:00 GMT would pass any WAF rule, any header validation, any logging filter. The only thing wrong with it is the date is in the future — and that’s enough to make the origin return 304, which the CDN dutifully caches, denying content to everyone. The lesson generalises: when you think you’ve covered an attack class, go read the academic literature. Researchers systematically enumerate possibilities in ways that practitioners (myself included) don’t. WAF-as-attack-vector is a configuration problem, not a WAF problem. WAF poisoning isn’t a vulnerability in the WAF itself. The WAF is doing exactly what it’s configured to do: block requests that match attack signatures. The vulnerability is the interaction between the WAF and the cache layer. If the WAF’s 403 block page gets cached and served to clean requests, the WAF has become the attack. The fix is either configuring the CDN to never cache 403 responses, or configuring the WAF to add Cache-Control: no-store to block pages. Neither is the default on most platforms, which is why HCache found this pattern on 225 sites across the Tranco Top 1K. Your HTTP library’s transport layer is a hidden filter. When I added metacharacter injection payloads, I discovered that h11 (Python’s HTTP/1.1 parser, used by httpx, uvicorn, and Starlette) silently rejects requests containing \x00 , \x0A , \x0B , \x0C , or \x0D in header values. The rejection happens at the transport layer before the request is ever sent. This means any scanner using httpx literally cannot test five of the most interesting control bytes. The workaround is to only test the control bytes that h11 allows through — \x01 , \x08 , \x1b , \x7f — and accept that the remaining bytes would require a raw socket or a different HTTP library to test. I eventually did add raw socket support for one specific case: the illegal header name injection module (Akamai CP-DoS), where the attack requires characters in header names that h11 also rejects. But for header value testing, the h11 filter remains. The lesson: know your tools’ implicit constraints, because they silently narrow your test coverage. # 
What’s Next The pipeline described here covers cache poisoning and cache deception as independent attack classes. The highest-impact next step is automated chain detection — specifically, combining cache deception with Client-Side Path Traversal (CSPT). The CSPT-cache deception chain is responsible for the ChatGPT ATO and Zere’s account takeover write-up. The pattern: find JavaScript that makes a fetch call with user-controlled path segments ( fetch(\ /api/users/${userId}`)`), then use a cache-deceptable path with a traversal payload to make the victim’s browser request a sensitive endpoint via the CSPT sink, causing the CDN to cache their authenticated response. Detecting this chain requires static analysis of target JavaScript to find CSPT sinks, combined with the cache deception findings from cache_diff . I have the cache side built. The JS analysis side integrates with my existing tooling (self-developed and third-party) for taint-traced DOM analysis. The CSPT sink detection prototype identifies fetch() and XMLHttpRequest calls with user-controlled path segments in target JavaScript — the remaining work is integrating it with cache_diff output (matching delimiter mismatches to CSPT sinks on the same origin) and reducing the false positive rate on minified JavaScript to a level acceptable for unattended scanning. # 
Known Limitations No tool covers everything. These are the gaps I’m aware of: Transport-layer byte filtering. Python’s h11 HTTP parser rejects five control bytes ( \x00 , \x0A , \x0B , \x0C , \x0D ) at the transport layer before requests are sent. The metacharacter injection module can only test the bytes h11 allows through in header values . I’ve partially addressed this for header names — the illegal header name injection module drops to raw TCP sockets to bypass h11’s validation, specifically for Akamai CP-DoS testing. But for header values, exhaustive control-byte testing would still require a modified HTTP library or raw sockets throughout the scanner — a trade-off I haven’t made, since h11/httpx provides reliable HTTP/2 support that raw sockets would sacrifice. Priming heuristic is blunt. The 20-request internal cache priming is a fixed number, not adaptive. Caches with sub-second TTLs, write-through invalidation, or probabilistic eviction may need different priming strategies. For now, “20 requests and check” is good enough for most application-level caches, but it’s not optimal. No JavaScript analysis (yet). The cache deception module finds path delimiter mismatches but doesn’t analyse target JavaScript for Client-Side Path Traversal sinks. The CSPT chain — where a cache-deceptable path is used via a JavaScript fetch sink — is currently detected only through manual review. Automated CSPT detection is the primary planned addition (see What’s Next). Single-request oracle assumption. The cache key oracle sends one prime request followed by one verify request. This works for CDN-level caches but can produce false negatives against multi-layer cache stacks where different layers have different TTLs or key configurations. The multi-request priming mode partially addresses this, but a truly robust oracle would need to account for cache hierarchy. # 
A Note on Use This toolkit is designed for authorised security testing — bug bounty programs, penetration tests with written scope, and security research on infrastructure you own or have explicit permission to test. Cache poisoning, by definition, affects shared infrastructure. An unkeyed header that poisons a CDN cache can serve malicious content to real users. Every scan mode includes cache busters to isolate test requests, but no isolation is perfect. Test responsibly. #
